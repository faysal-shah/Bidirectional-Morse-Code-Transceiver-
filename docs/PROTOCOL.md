# MorseLink — Communication Protocol Specification

> **Version:** 1.0  
> **Transport:** IEEE 802.11 (Wi-Fi PHY) via ESP-NOW  
> **Security:** AES-128-CBC + HMAC-SHA256 (Encrypt-then-MAC)

---

## 1. Overview

MorseLink uses **ESP-NOW** — a connectionless Wi-Fi protocol by Espressif that
allows two or more ESP32 nodes to exchange short data frames (≤ 250 bytes) with
sub-10 ms latency and no access point. The payload of every ESP-NOW frame is
encrypted and authenticated before transmission.

```
Device A                                Device B
   │                                       │
   │  esp_now_send(peer_mac, packet)        │
   │ ────────────── 802.11 ────────────►   │
   │                                       │  onDataReceived()
   │                                       │  → verify HMAC
   │                                       │  → AES-CBC decrypt
   │                                       │  → display message
```

## 2. Physical / Link Layer

| Property       | Value                                      |
|----------------|---------------------------------------------|
| Protocol       | ESP-NOW (Espressif proprietary over 802.11) |
| Frequency      | 2.4 GHz Wi-Fi (no router required)          |
| Channel        | Configurable (default: **6**)               |
| Max payload    | 250 bytes per frame                         |
| Typical range  | 50–200 m open air (varies by environment)   |
| Latency        | < 10 ms end-to-end in LOS conditions        |
| Address scheme | 6-byte MAC; defaults to broadcast           |

## 3. Packet Structure

Every MorseLink transmission is a single ESP-NOW frame with the following layout:

```
 0        1        2        3        4        5        6        7   byte
 ┌────────┬────────┬────────┬────────┬────────┬────────┬────────────────┐
 │ Magic  │ Magic  │  Ver   │  Type  │ Src ID │ Dst ID │  Seq (16-bit)  │
 │  0x4D  │  0x4C  │  0x01  │        │        │        │  LE byte order │
 ├────────┴────────┴────────┴────────┴────────┴────────┴────────────────┤
 │ DataLen (1 B) │  Encrypted Payload (DataLen bytes, max 202 B)        │
 └───────────────┴───────────────────────────────────────────────────────┘
```

### 3.1 Header Fields

| Field     | Size   | Description                                               |
|-----------|--------|-----------------------------------------------------------|
| `magic`   | 2 B    | `0x4D 0x4C` ("ML") — rejects alien frames quickly        |
| `version` | 1 B    | Protocol version (currently `0x01`)                       |
| `type`    | 1 B    | Packet type (see §3.2)                                    |
| `src_id`  | 1 B    | Sender's `DEVICE_ID` (0–254)                              |
| `dst_id`  | 1 B    | Target's `DEVICE_ID`; `0xFF` = broadcast                  |
| `seq`     | 2 B    | Rolling counter; aids deduplication on retransmit         |
| `data_len`| 1 B    | Length of the encrypted payload that follows              |

### 3.2 Packet Types

| Value  | Name         | Direction   | Description                                  |
|--------|--------------|-------------|----------------------------------------------|
| `0x01` | `PKT_MSG`    | Peer → Peer | Encrypted text message                        |
| `0x02` | `PKT_ACK`    | Peer → Peer | Delivery acknowledgement (future)             |
| `0x03` | `PKT_PING`   | Any         | Keepalive / RSSI probe (future)               |

## 4. Encrypted Payload (for PKT_MSG)

The encrypted payload written by `cryptoEncrypt()` has the following internal
structure:

```
┌──────────────────┬──────────────────────────┬──────────────────────────────┐
│  Random IV       │  HMAC-SHA256 digest       │  AES-CBC ciphertext          │
│  (16 bytes)      │  (32 bytes)               │  (ptLen rounded up to AES    │
│                  │                           │   block size, PKCS#7 padded) │
└──────────────────┴──────────────────────────┴──────────────────────────────┘
```

Total overhead: **48 bytes** per message.  
Maximum plaintext: 250 − 8 (header) − 48 (crypto overhead) = **194 bytes**.  
`MAX_MSG_CHARS` is set to 120 for a comfortable margin.

## 5. Security Design

### 5.1 Encryption — AES-128-CBC

* **Algorithm:** AES with a 128-bit key in Cipher Block Chaining (CBC) mode.
* **Key:** Pre-shared symmetric key configured at compile time (`AES_KEY` in
  `config.h`). Change this before deploying in any real-world environment.
* **IV:** 16 bytes of fresh randomness generated by the ESP32's hardware TRNG
  (`esp_fill_random`) for every message. This ensures identical plaintexts
  produce different ciphertexts.
* **Padding:** PKCS#7 — the final block is padded with bytes of value equal to
  the number of padding bytes added.
* **Library:** mbedTLS (bundled with the ESP32 Arduino core / ESP-IDF).

### 5.2 Authentication — HMAC-SHA256

* **Scheme:** Encrypt-then-MAC. The HMAC is computed over `IV || ciphertext`,
  preventing any tampering with either field.
* **Key:** Separate 16-byte HMAC key (`HMAC_KEY` in `config.h`).
* **Comparison:** Constant-time byte comparison to defeat timing side-channels.
* **Effect:** Any attacker who does not know `HMAC_KEY` cannot forge a valid
  packet that the receiver will accept.

### 5.3 Threat Model & Limitations

| Threat                          | Mitigated? | Notes                                              |
|---------------------------------|-----------|----------------------------------------------------|
| Passive eavesdropping           | ✓         | AES-128-CBC with per-message random IV             |
| Message tampering               | ✓         | HMAC-SHA256 authentication                         |
| Replay attack                   | Partial   | Sequence numbers tracked; no persistent state      |
| Denial of service (flooding)    | ✗         | ESP-NOW has no rate limiting at the protocol level |
| Key extraction (physical)       | ✗         | Keys live in flash; use NVS encryption for strong security |
| Long-term key compromise        | ✗         | No forward secrecy (static PSK); rotate periodically |

> For applications requiring stronger security guarantees (e.g., field
> deployment), consider rotating the PSK via an out-of-band channel and
> storing it in encrypted NVS partitions.

## 6. Addressing & Pairing

The default `PEER_MAC_ADDR` is the broadcast address `FF:FF:FF:FF:FF:FF`.
This is convenient for initial setup but means any nearby MorseLink device
with the same PSK can receive your messages.

**To pair exclusively:**

1. Boot both devices; observe the Serial output: `[COMM] MAC → XX:XX:XX:XX:XX:XX`
2. Copy each device's MAC address.
3. Update `PEER_MAC_ADDR` in `config.h` of **Device A** to Device B's MAC, and
   vice versa.
4. Re-flash both devices.

After pairing, ESP-NOW will only route frames to the registered MAC address at
the link layer, even before the payload is decrypted.

## 7. Message Flow Example

```
 Device A types "HI" in Morse:          Device B receives
 ─────────────────────────────          ────────────────────────────
 press · · · ·  → H                    onDataReceived()
 wait 0.9s      → commit 'H'           HMAC-SHA256 verified ✓
 press · ·      → I                    AES-CBC decrypted
 wait 0.9s      → commit 'I'           msgBuf = "HI"
 press [SEND]                          SCREEN_RECEIVED shown
   AES-128-CBC encrypt("HI")           rxMsg = "HI"
   HMAC-SHA256 tag appended            buzzer: two ascending beeps
   esp_now_send()
   LED blinks on GPIO 2
```
